### Task 3 — GlobalExceptionHandler ⚠️ Partial

**File:** `exception/handler/GlobalExceptionHandler.java`

Present and annotated with `@RestControllerAdvice`. Handlers found:

| Method | Exception handled | HTTP status |
|--------|------------------|-------------|
| `handleResourceNotFound` | `ResourceNotFoundException` | 404 |
| `handleBusinessException` | `BusinessException` | 400 |
| `handleValidationException` | `MethodArgumentNotValidException` | 400 |
| `handleConstraintViolationException` | `ConstraintViolationException` | 400 |
| `handleHttpMessageNotReadableException` | `HttpMessageNotReadableException` | 400 |
| `handleApplicationException` | `ApplicationException` | (uses `ex.getStatus()`) |
| `handleGenericException` | `Exception` | 500 |

**Problem — duplicate handler / shadowing:**

`ResourceNotFoundException` and `BusinessException` both extend `ApplicationException`. Spring picks the **most specific** handler, so the dedicated handlers (`handleResourceNotFound`, `handleBusinessException`) will fire correctly. However, the presence of a `handleApplicationException` that also catches `ApplicationException` is redundant for those two subclasses. If new `ApplicationException` subclasses are added in the future without a dedicated handler, they will fall into `handleApplicationException` — which is fine, but the code can be simplified.

**More importantly:** the two specific handlers (`handleResourceNotFound`, `handleBusinessException`) accept `HttpServletRequest` while all other handlers accept `WebRequest`. This inconsistency is functional but inconsistent, and mixing both in the same class can cause confusion. The `buildResponse` method is overloaded for both signatures, which resolves the compilation issue, but it is worth standardising.

**Verdict:** Functionally correct, no handler is truly broken. Minor architectural concern with redundant/inconsistent handler signatures.

### Task 5 — DTOs ⚠️ Partial

#### AlunoRequestDTO

**File:** `dto/request/AlunoRequestDTO.java`

**✅ Email is not `@NotBlank`:**
```java
@Email(message = "Informe um email válido")
@Size(max = 150, message = "O email do aluno deve ter no máximo 150 caracteres")

```
No `@NotBlank` — correctly optional.

**✅ Cross-field validation via `@AssertTrue`:**
```java
@AssertTrue(message = "O email do aluno é obrigatório quando não há responsável")
public boolean isEmailObrigatorioQuandoSemResponsavel() {
    return responsavelId != null || (email != null && !email.isBlank());
}
```
This is the correct approach for cross-field validation on a record. The logic is: pass if there IS a responsável OR if email is present. This correctly implements the business rule.

**⚠️ Naming convention issue with `@AssertTrue`:**  
Spring's `MethodArgumentNotValidException` reports the field name by stripping the `is` prefix from the method name. So this will produce a field error named `emailObrigatorioQuandoSemResponsavel` in the error response. This is not broken, but the error message will appear under a non-obvious field name. Consider renaming the method or accepting this behaviour.

**✅ All 6 agenda fields present:**
```java
@NotNull(message = "A forma de pagamento do aluno é obrigatória")
String formaPagamento,

@NotNull(message = "O valor mensal do aluno é obrigatório")

String diaSemanaPadrao,
LocalTime horarioPadrao,
Integer duracaoPadraoMin,
BigDecimal valorPadrao
```

All 6 fields are present. `formaPagamento` and `diaSemanaPadrao` are received as `String` and converted via `valueOf` in `toEntity()` — this is acceptable but will throw an unchecked `IllegalArgumentException` on invalid values. The `GlobalExceptionHandler` does not catch `IllegalArgumentException` specifically; it falls to the generic 500 handler. This should be caught with a `try/catch` in `toEntity()` or handled in the handler.

**✅ `toEntity()` mapping:**  
All fields correctly mapped, including enum conversion with null-safe guards.

### Task 6 — Controllers ⚠️ Partial

All 4 controllers follow the same pattern. Evidence from `AlunoController`:

```java
@PostMapping
public AlunoResponseDTO create(@RequestBody @Valid AlunoRequestDTO alunoRequestDTO) {
    return AlunoResponseDTO.fromEntity(alunoService.create(alunoRequestDTO.toEntity()));
}

@PutMapping("/{id}")
public AlunoResponseDTO update(@PathVariable UUID id, @RequestBody @Valid AlunoRequestDTO alunoRequestDTO) {
    return AlunoResponseDTO.fromEntity(alunoService.update(id, alunoRequestDTO.toEntity()));
}
```

**✅ Correct:**
- `@RequestBody @Valid` is present on all mutating endpoints in all 4 controllers.
- ResponseDTO is used in all return types.
- RequestDTO is used in all `@RequestBody` parameters.
- Dependency injection via constructor (no `@Autowired` field injection).

**⚠️ `create` returns 200 instead of 201:**  
All 4 controllers' `create` methods return a plain `AlunoResponseDTO` (or similar) with no `ResponseEntity`. Spring defaults this to HTTP 200 OK. The standard REST convention for a POST that creates a resource is 201 Created. Fix: wrap the return in `ResponseEntity.status(HttpStatus.CREATED).body(...)`.

**⚠️ No `@RequestMapping` version prefix:**  
Paths are `/alunos`, `/aulas`, `/professores`, `/responsaveis` — no `/api/v1/` prefix. This is not wrong per se, but worth noting for a production API.

**Verdict:** Functionally correct validation flow. The main gap is the HTTP 201 vs 200 status on creation endpoints.

### Task 7 — Services ⚠️ Partial

All services follow the same structure: constructor injection, `findAll`, `findById`, `create`, `update`, `deleteById`, and a private `updateXxx` merge helper.

**✅ Correct pattern:**
- `findById` throws `ResourceNotFoundException` on missing record.
- `create`/`update` throw `BusinessException` for null input.
- Repositories accessed via injected interface — no direct entity manager.

**⚠️ Email/responsável business rule NOT enforced at service level:**

`AlunoService.create` and `AlunoService.update`:
```java
public Aluno create(Aluno aluno) {
    if (aluno == null) {
        throw new BusinessException("Dados do aluno não informados.");
    }
    return alunoRepository.save(aluno);
}
```

There is no check: `if (aluno.getResponsavelId() == null && (aluno.getEmail() == null || aluno.getEmail().isBlank())) throw new BusinessException(...)`.

The cross-field rule is only enforced via the DTO's `@AssertTrue`. This is acceptable for the `create` flow (request → DTO → `@Valid` → entity). However, for the `update` flow the same DTO path is used, so it is also covered. The service-level gap only matters if the service is called programmatically without going through the DTO. Adding a guard in the service would make the rule truly airtight regardless of call origin.

**⚠️ `updateAluno` does not copy the `email` field:**

```java
public void updateAluno(Aluno aluno, Aluno obj) {
    aluno.setProfessorId(obj.getProfessorId());
    aluno.setResponsavelId(obj.getResponsavelId());
    aluno.setNome(obj.getNome());
    aluno.setTelefone(obj.getTelefone());
    aluno.setEndereco(obj.getEndereco());
    aluno.setFormaPagamento(obj.getFormaPagamento());
    aluno.setValorMensal(obj.getValorMensal());
    aluno.setDiaSemanaPadrao(obj.getDiaSemanaPadrao());
    aluno.setHorarioPadrao(obj.getHorarioPadrao());
    aluno.setDuracaoPadraoMin(obj.getDuracaoPadraoMin());
    aluno.setValorPadrao(obj.getValorPadrao());
}
```

`aluno.setEmail(obj.getEmail())` is **missing**. A PUT on an aluno will never update the email — it will silently retain the old value. This is a real bug.

**Verdict:** Partial. Two concrete bugs — missing email in `updateAluno`, and absence of a service-level safety guard for the email/responsável rule.
